# Security review 2 fixes ✅

_Moved from `PLAN.md` on 2026-10-24, as it stood._

Wallie asked for a second security review (2026-10-19) and chose four of its findings: the shared-photo device key in a header (other sites could make visitors' browsers upload photos through their US addresses), `Cross-Origin-Resource-Policy: same-origin` on every response, invisible and direction-reversing characters removed from names, and a limit on photo uploads at once. Its other findings repeat the first review's open fixes 1 and 7.

| # | Step | Status |
|---|---|---|
| 1 | **Shared-photo device key in `X-Reporter-Key`**, as for a photo on an entry, so a cross-site page can't send the upload without a preflight (there is no CORS policy). `SharePhotoForm` binds with `[AsParameters]` (header key, form files), so its validator still covers the key; the request-type guard test learned that an `[AsParameters]` record's form field is reported as the endpoint's request type. Tests red first (a key only in the form → 400 `reporterKey.required`; `api.test.ts` checks the header); perturbed: reading the key from the form again is caught, and so is a missing validator. | ✅ |
| 2 | **`Cross-Origin-Resource-Policy: same-origin`** on every response (`SecurityHeaders.cs`). `SecurityHeadersTests` (page, deep link, API, 404) and the photo-file test, red first. Not checked in a browser against the production build (the E2E run's Vite pages send no headers); every file the site loads is its own. | ✅ |
| 3 | **Names cleaned on write**: control and format characters removed (except ZWJ and ZWNJ), then trimmed — nicknames, place names, the admin's typed name, the hide note. Existing data unchanged (Wallie's choice). `Validation/DisplayText.cs`; each request record has a `Clean*` property its validator checks and its handler stores. Tests red first (21 `DisplayTextTests`, API tests for feedings, sightings, rename, spots, shared photos, admin rename/merge, the typed admin name and the note); perturbed: storing the raw nickname, validating the raw spot name and skipping `Clean` for the admin name are each caught. Test sources hold the characters only as escapes. | ✅ |
| 4 | **Photo uploads at once**: 4, no queue, a 5th gets 429 (`RateLimiting:PhotoUploadsAtOnce`). A global limiter (an endpoint policy would replace the `writes` limit) on endpoints with `PhotoUploadEndpoint` metadata, which `WithPhotoUploadLimits` adds. `PhotoUploadLimitTests` hold uploads while their files are stored (the test server only dispatches a request once its body is all sent, so holding the body open held nothing — found by a probe, then deleted); perturbed: no global limiter, no metadata — both caught. A 429 shows the page's existing upload error with Retry. Changing the setting in Azure: `infra/README.md` → Settings (a later `provision.sh` run drops it). | ✅ |
