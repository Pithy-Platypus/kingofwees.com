# KingOfWees.Server

- **Minimal APIs only.** Map endpoints with `MapGroup`/`MapGet`/`MapPost`; no controllers, no `AddControllers()`/`AddMvc()`.
- **Validate with FluentValidation only.** One `AbstractValidator<T>` per request type, failures carry `.WithErrorCode("field.reason")` — the client translates codes, so never rely on messages. DataAnnotations attributes are not wired up (there is no `AddValidation()`): they compile and silently validate nothing.
- **New endpoints go in a route group that has `ValidationFilter`** (today: `/api/king`, `/api/admin`, and the `/api` groups of `/api/version` and `/api/client-diagnostics`). An endpoint mapped outside such a group skips validation; the guard test `Every_request_body_and_query_type_has_a_FluentValidation_validator` catches a missing validator, not a missing filter. Query-string requests bind through an `[AsParameters]` record — that's what the guard and the filter see; loose query parameters go unvalidated.
- **Text people type for others to see is validated and stored only through `DisplayText.Clean`**, via the request's `Clean*` property (validator rule with `OverridePropertyName`, and the handler) — nicknames, place names, the admin's typed name, the hide note. A new name field stored or checked raw works and passes every test, and lets a name read backwards (U+202E) or pass for another (a zero-width space). Never add a hand-made list of characters: `Clean` removes whole Unicode categories.
- **"Seen" means `SawKing`, not `Kind == Seen`.** Feedings count as sightings unless the food was left out. In Mongo filter with `Ne(SawKing, false)`: documents from before the flag have no field, and `Eq(true)` silently drops them.
- **Every public read in the event, spot and photo stores leaves out hidden entries and hidden devices** — `Visible()` in `MongoKingEventStore` and `MongoPhotoStore` (a photo also leaves with its entry: `Nin(EventId, hidden entries)`), `Nin(ReporterKey, …)` in `MongoSpotStore.ListAsync`, and the same in the in-memory doubles. A new read method without it shows spam to everyone and every existing test still passes. `FindAsync` deliberately skips it (undo, rename and history cursors need hidden entries), and so does `FindManyAsync` (a page of photos looks up its entries with it, `/admin`'s hidden photos included), as does `IPhotoStore.FindByEventAsync` (one photo per entry, hidden or not), and so do `ISpotStore.NameTakenAsync` and `ListEveryAsync`, admin-only (a hidden device's place still blocks its name — or restoring the device brings back a duplicate — and admins rename it from the full list), and the merge methods `IKingEventStore.MoveFeedingsAsync` / `CountEveryFeedingBySpotAsync` and `ISpotStore.DeleteAsync` (a hidden feeding left unmoved would point at a deleted place, and the confirmation would undercount what moves). Filter the entry flag with `Ne(Hidden, true)`: documents from before the flag have no field, and `Eq(false)` drops them all.
- **Coordinates exist only as `GeoPoint`**, which rounds to 3 decimals whenever a coordinate is set (constructor, `with`, JSON, configuration). Never add raw latitude/longitude `double`s to a request, domain record or options class — they bind, store and return unrounded with nothing failing. A Mongo document may hold the two doubles only copied from a `GeoPoint`, and rebuilds one on read.
- **Public writes go only in the `/api/king` writes group (`KingEndpoints.MapKingEndpoints`)** — it alone carries `CanPost`, the write limit and `PostingCountryFilter` (US-only posting). A write mapped elsewhere works and is open to every country. The one exception is `POST /api/client-diagnostics` (`Diagnostics/ClientDiagnostics.cs`): it stores nothing and only logs, and must stay open to every country (a visitor abroad seeing a broken page matters too); anything that stores what a visitor sent goes in the writes group. Keep the US check a filter, not part of `CanPost`: a failed policy for an anonymous visitor is a 401 challenge, which the page reads as something else and which runs the admin sign-in audit. Unknown addresses stay allowed, and never check the MMDB's database type (DB-IP's says `DBIP-Country-Lite`).
- **Store only what `JpegMetadata.Strip` returns for an uploaded photo**, never the uploaded bytes: the browser's re-encode drops the GPS point, but anyone can post to the endpoint directly, and a stored EXIF block publishes a location more exact than a block. Photo writes (`PhotoEndpoints.MapPhotoWrites`) are mapped only on the writes group above, and take the device key only from `X-Reporter-Key`, never a form field: a key in the form works and passes every test, and lets any other site make visitors' browsers post through their US addresses (a form post needs no preflight; a custom header does).
- **Photo files are served `Cache-Control: private` with a short `max-age` (an hour)**, never `public`/`immutable`: a long or shared cache looks right — the files never change — and keeps a photo an admin hid on screens and in any proxy cache.
- **`[FromForm]` request records use `init` properties, not constructor parameters** (`AddPhotoForm`, `SharePhotoForm`). Form binding treats every constructor parameter as required: a missing optional field becomes a bare 400 with no error codes, before the US check runs.
- **Admin endpoints go only in the `/api/admin` group (`Admin/AdminEndpoints.cs`)** — it alone carries the `Admin` policy, the admin rate limit and `ValidationFilter`. An admin endpoint mapped under `/api/king` works and is open to everyone.
- **Every admin change records itself through `AdminAudit.RecordAsync` after it succeeds**, saying what it touched in words (names, counts, places — never a device key or entry id). A new admin endpoint without it works, passes every existing test and leaves no trace in the audit log. Wrong keys are recorded only in `AdminSignInAudit`. `IAdminLogStore` stays append-only, and the log's `AtUtc` stays a `DateTime`: its TTL index silently skips any other BSON type, so records would never expire.
- **Never log, tag or return the admin key or the `Authorization` header, and never log or tag the typed admin name (`X-Admin-Name`) or a hidden photo's note** — they live only in the audit log (and, for the note, on the photo while it stays hidden). Configuration holds only the key's hash (`King:Admin:KeyHash`), made by `source/tools/new-admin-key.cs`; never hash keys by hand or add a setting that holds the key itself.
- **Rate limits key on `Connection.RemoteIpAddress`, which is the visitor only because `UseForwardedHeaders` runs first in `Program.cs` when `King:Proxy:TrustForwardedFor` is set.** Behind Container Apps' ingress, without it every visitor shares one bucket; with it set where Kestrel is reachable directly, or with more than one hop trusted, anyone picks their own address. Set it only in the Container Apps deployment; keep `ForwardLimit = 1` and the middleware ahead of `UseRateLimiter`.
- **Every `/api/king` route is under the `reads` limit from its group, and a `RequireRateLimiting` closer to the endpoint replaces it — it doesn't add to it.** That's how writes and photo files count only against their own limits. A new route that sets its own policy leaves the read limit; a high-volume read (many per page, like thumbnails) needs its own policy, or it locks visitors out of everything else. A new limit setting also goes in `KingApiFactory` and the E2E `AppFixture`, which make every request from one address.
- **Kestrel caps every request body at 64 KB (`Program.cs`); an endpoint that takes more carries its own `RequestSizeLimitAttribute`, as the photo uploads do (`WithPhotoUploadLimits`).** The test server enforces neither, so a bigger endpoint without it passes every test and answers 413 in production. A new upload endpoint goes through `WithPhotoUploadLimits`, whose `PhotoUploadEndpoint` metadata also puts it under the uploads-at-once limit (the global limiter in `KingServices`); one without it works and lets any number of multi-megabyte uploads into the 0.5 GiB app at once. Never put that limit in an endpoint policy: it would replace the `writes` limit, not add to it.
- **`/health` and `/alive` are mapped in every environment (`MapDefaultEndpoints`), and `/alive` checks only `live`-tagged checks.** Wrapping them in `IsDevelopment()` (as the Aspire template does) looks harmless: in production the SPA fallback then answers `/health` with `index.html` and a 200, so the probe passes with the database down. Adding the database to `/alive` makes a database outage restart the app in a loop. Keep the default response writer — no check details. The photo storage client (`AddAzureBlobContainerClient("photos")`) runs with `DisableHealthChecks = true`: Aspire's default adds it to `/health`, and a photo-storage outage would then take the whole site offline.
- **A counter goes on the `KingOfWees` meter (`KingMetrics`), never a meter of its own.** With `APPLICATIONINSIGHTS_CONNECTION_STRING` set, a View drops every other instrument before the Azure Monitor exporter (the runtime and ASP.NET Core ones alone pass the daily cap), so a new meter shows up in the Aspire dashboard and every test and never reaches Application Insights. The exporter's own performance counters and standard metrics are off in the same `Configure` (`Extensions.cs`).
- **Only `/api` paths are traced (the ASP.NET Core instrumentation's `Filter` in `Extensions.cs`), and a span that is noise is dropped in `Telemetry/NoiseFilter` — never by a sampler or a lower `SamplingRatio`.** A page, file or health request traced again is an unlimited row source anyone can use to spend the workspace's daily cap (then no alert fires until 18:00 UTC); a sampler would lose a post's row with its email. A new `/api` route is traced by default and must stay under a rate limit.
